# 常见失败模式

| 错误做法 | 正确做法 |
|---|---|
| 用 mock 数据验证通过就宣称完成 | 用真实数据源跑通最小闭环并记录证据 |
| 只读代码就说逻辑没问题 | 实际执行，以输出和持久化结果为证据 |
| API 返回 200 就当成功 | 断言具体业务字段、错误语义和下游可用性 |
| 改代码后再补 spec | 范围或规则变化时先更新 dev spec |
| 验证失败后扩大改动面 | 定位根因，只改最小必要范围 |
| 每次任务全量读文档 | 按 AGENTS 路由读取最少但足够的资料 |
| 阶段结束不更新状态 | 回写当前状态、验收记录、风险和下一步 |
| 用 dev spec 推翻 AGENTS 硬约束 | 按优先级执行，不能绕过安全与测试规则 |
| 未授权就在 sandbox/生产执行写操作 | 先确认环境和影响范围，生产写操作需明确授权 |
| 把专项 Skill 的流程当验收标准 | 专项 Skill 管方法，dev spec 管完成标准 |
| 把 WIP 提交描述为已交付 | 使用 WIP/partial，并记录未验证原因 |
| 交接只说“已完成” | 提供阶段、验收、证据、限制和下一步 |
| 在聊天里口头确认后继续开发但不写入文件 | 确认必须先落盘到 AGENTS.md、dev spec 或关联规范，再继续实现 |
| 每个会话重复询问已确认的信息 | 优先读取当前有效决策与验证记录，仅询问新缺口或被新证据推翻的决定 |
| 规范建立本身无限扩张 | 先建立最小启动规范，其余章节随阶段按需补全 |
| 为每个实现细节逐一暂停提问 | 先汇总本阶段必须确认的决策包；命名、顺序、可替换映射等用暂定假设推进 |
| 用户确认边界后仍只写规范、不执行行动 | 同一轮落盘决定后，立即执行下一项安全且有价值的只读验证或最小实现 |
| 把完整项目问卷当作启动前置条件 | 只收敛当前阶段会影响范围、验收、权限或不可逆操作的决定；未知事项随证据补充 |
| 设计获批后直接说“开始 P1” | 开始 L2/L3 前，在聊天中展示完整阶段路线图、总阶段数和当前阶段启动卡 |
| 只给 dev spec 链接，假定开发者知道总计划 | 路线图必须直接输出；仅在阶段拆分实质变化时再要求确认 |
| 把“先写规范”理解为已授权执行 | 以用户最新明确指令判断本轮授权范围；仅设计时状态为“待开发者确认” |
| 专项 Skill 逐题澄清，打断规范建立 | 阶段治理由 spec-driving 管；当前阶段全部关键决定必须打包呈现 |
| 把“含执行”理解成完整工程化 | 先判定阶段形态；有关键未知事实时走证据优先 |
| 关键外部事实未证明就建 worktree、数据库、CLI 或批量框架 | 先取得决定性真实边界的首次证据，再决定是否工程化 |
| 把 Git 初始化、详细计划或分支当作阶段启动门票 | Git 与计划是可选机制；不得因此暂停已授权的首次证据 |
| 用测试数量、审查轮次或文档篇幅汇报进展 | 以阶段里程碑与真实证据汇报 |
| 用户已说“开始做”后仍为低风险手段反复要批准 | 授权覆盖首次证据；仅新权限、不可逆操作或核心范围变化才重问 |
| 证据优先阶段自动启用完整 TDD、worktree 或并行审查链 | 只有项目规则、隔离要求或证据可信度需要时才按需使用，并记录必要性 |
| 证据批次未达成后扩大工程规模或隐性扩展范围 | 同范围内可走已记录的低风险替代路径；扩范围、权限或操作面先改阶段契约并走决策包 |
