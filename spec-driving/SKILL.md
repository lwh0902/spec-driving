# Spec Driving

## 定位

使用本 Skill 将项目带入并持续保持在规范驱动的交付流程中。

本 Skill 管理三件事：

1. 做什么：范围、真实业务闭环、当前阶段；
2. 什么算完成：验收项、真实证据、完成定义；
3. 状态放在哪里：AGENTS.md、dev_spec.md 与计划文件；需要代码交付时再由 Git 历史追溯。

不要用本 Skill 替代需求探索、计划、测试、调试、评审或分支收尾的方法论。

```text
专项方法 Skill：如何执行
AGENTS.md + dev_spec.md：执行什么、以何种形态推进、什么算完成
```

## 项目启动流程

```text
显式使用 $spec-driving
  ↓
检查 AGENTS.md 与 docs/dev_spec.md 是否存在且足以覆盖当前任务
  ↓
判断本轮授权范围：仅设计 / 含执行
  ↓
缺失或信息不足
  ↓
只读调研 → 收敛本阶段决策包 → 确认必要事项
  ↓
写入 AGENTS.md + dev_spec.md → 设计审阅输出合同
  ↓
仅设计：待开发者确认 / 含执行：判定阶段形态后立即执行下一项安全行动
  ↓
回写真实证据 → 满足推进条件后实现或进入下一阶段 → 按需 Git 交付
```

不得用聊天上下文、临时假设或未落盘的口头结论替代项目规范。

## 优先级

发生冲突时，按以下顺序执行：

1. 平台、系统、开发者、工具与安全规则；
2. 用户最新明确指令；
3. AGENTS.md 中的项目硬性规则；
4. dev_spec.md 中的当前范围、阶段、依赖和验收；
5. 专项方法 Skill 的流程建议；
6. 其他项目文档与历史实现。

dev_spec.md 可以细化当前项目事实，但不得绕过 AGENTS.md 的安全、权限、测试或提交硬约束。

## 显式激活协议

用户显式使用 `$spec-driving` 时，先完成以下步骤，之后才可修改代码或执行外部写操作：

1. 检查项目根目录 AGENTS.md 与 docs/dev_spec.md 是否存在；
2. 存在时，阅读 AGENTS.md 与 dev spec 的“当前状态”；
3. 缺失或不完整时，执行“项目启动、决策包与规范建立”；
4. 按 AGENTS.md 文件路由读取任务必需资料；
5. 检查 Git 状态、当前分支和未提交改动；
6. 判断任务级别与适用的专项方法 Skill；
7. 判断“本轮授权范围”；
8. 若将开始 L2/L3，执行“阶段路线图可见门禁”及“阶段执行形态与首证据门禁”；
9. 输出设计审阅或阶段启动所需信息。

未显式调用但任务明显涉及多阶段交付、真实集成或长期维护时，建议用户使用本 Skill；仅在用户确认或 AGENTS.md 明确要求后执行本协议。

## 项目启动、决策包与规范建立

### 本轮授权范围

在建立规范、开始代码、发起外部请求或任何项目执行前，先依据**用户最新明确指令**记录本轮授权范围：

| 范围 | 典型指令 | 允许行动 | 阶段状态 |
|---|---|---|---|
| 仅设计/规范 | “先写清楚目标”“只做设计”“先审阅方案” | 本地只读检查、创建/更新规范、设计审阅输出 | 待开发者确认 |
| 含执行 | “开始做”“执行 P1”“试点查询”“实现并验证” | 在确认的范围内执行当前阶段第一项安全行动 | 设计中 / 联调中等实际状态 |

较早的“可以试试/后续要做”不覆盖用户最新的“先/只做设计”限制。若本轮范围不清楚，将“本轮是否允许进入当前阶段执行”作为阶段决策包的一项；不得把等待授权称为“被阻塞”。

仅设计/规范时，完成设计审阅输出合同后结束本轮，不启动采集、第三方查询、代码实现或其他项目执行。含执行时，适用“确认后的连续推进”。

### 阶段决策包

进入新阶段前，先收敛**当前阶段全部**必须由开发者确认的事项，形成一个决策包；不要把它们拆成连续的单题对话。

每项只包含：缺少的信息、推荐方案、可选替代方案、对范围/验收/风险的影响，以及推荐默认值（如适用）。一次覆盖当前阶段全部已知关键决定；通常控制在 3–7 项，更多时按相互独立的决策包分组一次呈现，而非抛出完整项目问卷或连续单题追问。

仅以下情况可列入必须确认项：

- 会改变目标用户、核心业务闭环、范围或验收标准；
- 数据源、账号、登录态、权限、合规或访问边界不明确；
- 生产写入、付款、订单、删除、发布等不可逆外部操作；
- 会锁定不兼容的 API/数据契约、数据归属或核心架构；
- 没有答案就无法定义本阶段的真实验证。

以下事项**不得**作为阻塞项：内部命名、URL 或 query 参数形式、实现顺序、默认展示、可替换映射、只读调研路径，以及可由真实验证推翻的低风险技术细节。

对非阻塞事项，采用推荐默认值并写入 dev spec 的“暂定假设”：写明其可逆理由、验证触发条件和状态。新证据出现时再修正，不必先等开发者逐项确认。

本 Skill 管项目治理节奏：在规范建立与阶段切换时，决策包优先于专项方法 Skill 的逐题澄清习惯。专项 Skill 可在已确认范围内继续其方法性探索，但不得把低风险实现细节拆成连续的开发者确认。

### 确认后的连续推进

当本轮授权范围为“含执行”且用户确认阶段决策包后，必须：

1. 先将结论落盘到 AGENTS.md、dev spec 或关联规范；
2. 在**同一轮**开始下一项安全且有价值的行动；L2/L3 先按“阶段执行形态与首证据门禁”确定行动规模，例如真实数据验证、接口探测或最小实现；
3. 在本阶段内持续推进，直到到达验收、真实阻塞或出现新的高风险边界。

不得只回复“已写入规范，尚不开始”。只有新证据推翻已确认决定，或出现上述必须确认项时，才允许重新暂停提问。仅设计/规范时按“本轮授权范围”结束于设计审阅，而不是强行执行。

### 阶段执行形态与首证据门禁

“含执行”不等于“完整工程化”。进入任何 L2/L3 阶段后，先判定阶段形态，再决定要调度的专项 Skill 和支撑工作。

| 形态 | 何时选用 | 首要目标 |
|---|---|---|
| 证据优先 | 存在关键未知事实；若不成立会推翻大部分后续工作 | 用最小真实行动证明或证伪该事实 |
| 实现优先 | 关键机制已有真实证据，需要稳定交付 | 按计划建设可维护实现 |
| 诊断优先 | 已有可观察异常、回归或性能问题 | 复现、定位根因、最小修复 |
| 轻量执行 | L0/L1，或范围明确、风险低的小改动 | 直接修改并验证 |

Agent 必须判定阶段形态并写入阶段契约。仅当该判定会改变范围、验收、权限、不可逆风险或显著资源投入时，才进入决策包请求确认。分类存疑时，采用“证据优先”作为可逆默认值，直接开始首次证据；不得为此重复索要确认。只有新证据满足阶段契约的推进条件后，才可从“证据优先”转为“实现优先”。

#### 阶段契约（L2/L3 必填）

每个 L2/L3 阶段在 dev spec 中维护：

```text
阶段形态：
阶段产出：          ← 开发者真正需要看到的可观察结果
关键不确定性：      ← 若不成立会推翻后续大部分工作的事实；无则写“无”
首次证据：          ← 最小、真实、可观察的决定性边界验证
证据前允许的支撑工作：
首次证据预算：      ← 一次可独立解释的证据批次
推进条件：          ← 满足什么后才可进入完整建设或下一阶段
```

首次证据必须触达最终交付链路中决定成败的真实边界，但不要求一次完成整个用户闭环。mock、内部单测通过、HTTP 200、脚手架搭好或文档写完，都不能替代它。

#### 证据优先的工作边界

在不牺牲证据可信度、可复核性和安全性的前提下，选择设置成本、状态变更和耦合最小的方法；优先复用已有能力。只有低成本方案不足以取得可信证据时，才增加数据库、自动化、worktree 或并行执行，并在阶段契约记录其必要性。

证据优先阶段不自动启用完整 TDD 套件、worktree、子代理并行、通用存储层、CLI 框架或多轮审查链。项目既有测试策略、隔离要求或证据可信度确有要求时，仍可按需使用；本门禁限制的是自动升级工程规模，不是禁止必要方法。

首次证据预算按阶段契约定义为“一次可独立解释的证据批次”，不使用全局固定次数或时长。一个证据批次未达成后：

- 可在既有范围与阶段契约内，采用已记录的低风险替代路径继续；
- 若需要扩大数据源、权限、操作面、范围或验收，必须先更新阶段契约，并按决策包规则处理；
- 不得通过扩大工程规模继续碰撞。

#### 授权连续性与里程碑

用户已明确“开始做”“执行 Pn”或同义指令后，授权至少覆盖当前阶段的首次证据（证据优先）或已确认阶段启动卡范围（实现优先）。除非出现新的权限边界、不可逆操作或核心范围变化，不得重新索要本不必要的批准。

Git 提交、分支、worktree、详细计划、数据库、CLI 和批量框架均是可选交付机制，不是启动阶段的门票。进度汇报必须以真实阶段里程碑为准，例如“已获得首条真实结果及字段证据”；不得用文档篇幅、测试数量或审查轮次冒充阶段进展。

### 设计审阅输出合同

设计、规范或阶段计划完成后，必须在**一条聊天消息**中向开发者输出以下内容；不得只给文档链接：

1. 总目标与关键约束；
2. 完整阶段路线图；
3. 当前阶段启动卡；
4. 本阶段待确认决策包与暂定假设；
5. 本轮授权范围；
6. 下一步：等待何种确认，或将立刻执行的第一项行动。

本轮为“仅设计/规范”时，明确写出“本轮未启动执行，状态为待开发者确认”；本轮为“含执行”时，设计审阅输出后立即开始已说明的第一项安全行动。

### 阶段路线图可见门禁

设计文档完成并获确认后、开始任何 L2/L3 实现前，必须从 dev spec 的阶段计划中向开发者直接输出完整路线图；不得只给文档链接或只宣布“开始 P1”。

路线图输出必须包含：

- 总目标、阶段总数和阶段编号范围；
- 每个阶段的目标、前置依赖、验收产物和当前状态；
- 当前将进入的阶段，以及它为何是下一步。

随后输出当前阶段启动卡：

```text
当前阶段：
本阶段目标：
不在本阶段的事项：
前置依赖及其验证状态：
本阶段验收项与真实验证方式：
```

若路线图只是已批准设计的透明展示，不额外要求开发者再次确认；若阶段拆分新增或改变范围、依赖、验收或风险，则先将变化放入阶段决策包并获得确认。路线图每次发生实质变化、或从设计进入首次实现时，必须重新展示，并在 dev spec 当前状态记录展示日期/版本。

### 新项目或规范缺失

若项目缺少 AGENTS.md 或 docs/dev_spec.md：

1. 先只读检查项目结构、已有文档、脚本、依赖和 Git 历史；
2. 判断当前信息是否足以定义目标、范围、阶段和验收；
3. 信息不足时，形成首个阶段决策包，请开发者一次确认其中的关键事项；
4. 信息确认后，创建或补全 AGENTS.md 与 docs/dev_spec.md；
5. 将已确认的目标、范围、阶段、验收、数据源、风险和决策写入文件，并将其余可逆事项记录为暂定假设；
6. 规范建立后，在同一轮执行下一项安全行动；在关键缺口未确认前，不开始 L2/L3 的代码、数据库或外部集成改动。

### 最小启动规范

不要让规范建立本身成为大型工程。满足以下最低内容即可开始 L2/L3：

- AGENTS.md：项目命令表、禁止事项、文件路由；
- dev_spec.md：目标与非目标、一个真实业务闭环、当前状态表、验收项、当前阶段决策包或暂定假设。

其余章节随项目阶段按需补全。

规范建立期间：

- L0（只读调研、解释、状态报告）始终允许；
- L1 仅在已有最小 dev spec、不会影响未决缺口、且能记录依据和结果时允许；
- L2/L3 必须等最小启动规范建立、关键缺口确认并落盘后才能开始。

### 规范不完整

已有 AGENTS.md 或 dev spec 但缺少当前任务需要的信息时：

- 先识别缺口；
- 判断其是否属于“阶段决策包”中的必须确认项；
- 属于时，汇总本阶段其余已知必须确认项后再询问开发者；
- 收到答案后，先更新对应文件，并在同一轮继续下一项安全行动；
- 不属于时，采用安全默认值，记录为暂定假设后继续。

### 避免重复询问

已询问、已确认并已落盘的缺口，不得重复询问。已被标记为暂定假设且尚无反证的事项，也不得重复询问。

仅当出现新的会影响当前任务的缺口、新证据推翻当前有效决策，或用户明确修改范围、验收或风险边界时，才重新暂停询问。

### 决策包格式

将当前阶段所有已知必须确认项放在一条消息中。每项使用：

```text
决策：
推荐方案：
替代方案：
影响：
推荐默认值（如适用）：
需要确认：
```

不要把纯偏好或低风险细节混入决策包。收到确认后，先将决定写入 AGENTS.md、dev spec 或关联规范，再执行同一轮的下一项安全行动。

## 专项方法 Skill 路由

先检查当前环境是否存在对应专项 Skill。存在时遵循其指引；不存在时采用本 Skill 的后备流程，不得因此跳过范围、验收、状态或真实验证要求。

| 场景 | 优先使用的专项 Skill | 本 Skill 的约束 |
|---|---|---|
| 新功能、需求不清、存在方案选择 | `brainstorming` | 将范围、闭环、非目标、验收写入 dev spec |
| 已确认的多步骤功能 | `writing-plans`、`executing-plans` | 仅在“实现优先”且推进条件满足后；证据优先时只做短证据计划 |
| 缺陷、异常、性能问题、测试失败 | `systematic-debugging` | 诊断优先；根因、证据、回归范围写入 dev spec |
| 适合自动化测试的新行为 | `test-driven-development` | 服从 AGENTS.md 测试策略与禁令；证据优先阶段不自动扩展为完整测试工程 |
| 收到代码评审意见 | `receiving-code-review` | 先验证意见，再决定采纳方式 |
| 重大功能完成或准备合并 | `requesting-code-review` | 评审不替代真实验收 |
| 准备宣称完成 | `verification-before-completion` | 该 Skill 管时机；本 Skill 管证据标准 |
| worktree、分支、PR 收尾 | `using-git-worktrees`、`finishing-a-development-branch` | 实现优先后按需；证据优先默认不启用 worktree，提交范围与阶段状态以 dev spec 为准 |

多个专项 Skill 同时适用时，先使用需求澄清或调试等过程类 Skill，再使用计划、实现、验证和收尾类 Skill。

## 文件职责

### AGENTS.md

每次开始任务前阅读。只放长期稳定的项目规则：项目结构、主要模块、命令、测试策略、Git 与分支规范、密钥与临时文件规则，以及任务资料路由。

需要建立或更新 AGENTS.md 时，读取 `references/agents-template.md`。

### docs/dev_spec.md

将其作为项目状态与验收控制中心。至少维护：当前状态、目标与非目标、真实业务闭环、系统边界、功能/API 清单、阶段计划、验收项、当前有效决策、决策历史、验证记录、风险、阻塞项和下一步。

需求、架构、接口语义、缓存策略、数据归属或验收方式变化时，先更新 dev spec，再改实现。

需要建立或更新 dev spec 时，读取 `references/dev-spec-template.md`。

### 计划文件

将详细实施计划放在 AGENTS.md 指定的位置。推荐 `docs/plans/YYYY-MM-DD-Px.y-feature.md`。计划必须引用阶段编号；dev spec 只保留计划链接、阶段状态和验收结果。

## 任务分级与阶段门禁

| 级别 | 场景 | 最低流程 |
|---|---|---|
| L0 | 只读检查、解释、状态报告 | 阅读规范并给出证据 |
| L1 | 明确的小修复、文案、局部样式 | 引用既有 spec，修改并验证 |
| L2 | 单接口、页面交互、数据行为 | 设计或计划、实现、真实验证、联调 |
| L3 | 跨模块、第三方、订单、支付、迁移、权限 | 需求澄清、书面计划、阶段门禁、真实验收 |

对新功能、阶段变更、接口语义变化或跨模块改动，必须定义或更新真实业务闭环。L0/L1 可引用已有闭环，不必重复设计。

将 dev spec 的“当前状态”作为当前阶段唯一状态来源：开始前确认依赖和未完成验收项；L2/L3 同时确认阶段契约及推进条件；当前阶段未满足推进条件或验收条件时，不进入依赖它的下一阶段；每次推进后立即更新状态、风险、阻塞与下一步。设计完成后、首次 L2/L3 实现前必须先通过“阶段路线图可见门禁”。

仅使用以下阶段状态：

```text
未开始 / 待开发者确认 / 设计中 / 已实现待验证 / 联调中 / 已验证 / 被阻塞 / 已废弃
```

“待开发者确认”表示设计或规范已足以展示，但本轮未获进入下一阶段的授权；“被阻塞”只用于外部依赖、权限、技术事实或关键决定使当前阶段确实无法继续的情形。

## 真实验证与完成定义

不要将“代码看起来正确”或 HTTP 200 视为完成。

| 类型 | 最低证据 |
|---|---|
| API | 真实请求，断言具体业务字段与错误语义 |
| 数据库 | 查询真实环境，核对字段、约束、行数或状态变化 |
| 前端 UI | 浏览器真实操作，确认元素、交互和结果状态 |
| 第三方集成 | sandbox 或获批准测试环境的脱敏请求/响应摘要 |
| 后台任务 | 真实触发一次，确认持久化或可观察结果 |
| 性能 | 记录耗时点、数据量、缓存命中和外部调用次数 |

数据等级：Mock 只用于隔离测试；Fixture 只用于可复现集成测试；真实测试数据可证明测试环境集成；生产数据仅用于只读验证或获明确授权的写操作。

以下操作默认需要用户明确授权：生产数据库写入；真实订单、支付、扣款、退款、发券、取消；邮件、短信、Webhook；云端密钥、权限或关键配置；推送或合并到 main、master、release 等受保护分支；force push；发布或部署。普通 feature 分支推送是否允许，由 AGENTS.md 规定。

记录验证证据时必须脱敏，不得写入密码、令牌、私钥、完整个人信息或生产敏感数据。

只有同时满足以下条件，才可宣称阶段或任务完成：

1. 实现完成，并执行 AGENTS.md 要求的检查命令；
2. 仅在项目测试策略允许且适用时新增或运行自动化测试；
3. 每个验收项都有真实验证证据；
4. dev spec 的当前状态、验证记录、风险、阻塞项和下一步已更新；
5. 交付路径中无未经批准的 mock、临时绕过或未说明 TODO；
6. 相关核心流程未发生回归，或回归风险已明确记录。

验证失败时，先定位根因，只改最小必要范围；不得借失败扩大改动面。同一假设连续失败两次时，停止并重读 dev spec 与相关规范；需要系统化排查时使用 `systematic-debugging`。执行前或发生偏差时，读取 `references/anti-patterns.md`。

## Git 提交与交接

提交前检查：

```bash
git status
git diff
git diff --cached
```

- 阶段性交付提交使用 `type(Px.y): 摘要`；
- 与阶段无关的维护提交遵循项目既有格式，但说明关联范围；
- 未验证代码允许提交，但标明 `WIP` 或 `partial`，并在 dev spec 记录原因；
- 不提交 `.env`、密钥、本地数据库、临时调试文件、敏感响应和无关改动；
- 提交说明必须如实表达交付范围。

恢复会话时，先阅读 dev spec 当前状态，再检查 Git 状态和最近提交，确认未完成验收项，汇报恢复结论后继续。

阶段推进、暂停或完成时，读取并使用 `references/handoff-template.md`。
